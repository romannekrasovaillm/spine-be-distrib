# Инструкция для агента: развёртывание arch-be с нуля

Контракт для ИИ-агента, которому передали бинарь `arch-be` (из этого
каталога) и задачу «поднять харнесс и подключить LLM». Выполняй шаги
по порядку; после каждого — проверка. Не пересобирай бинарь. Не пиши
значения ключей в конфиг, логи, ответы и файлы — только имена
env-переменных / пути файлов ключей.

## Термины

- `CONFIG` = `~/.config/arch-harness/config.toml` (создаётся на шаге 2).
- Порядок поиска конфига: `--config <path>` → `./arch-harness.toml` → `CONFIG` → встроенные дефолты.
- Встроено в бинарь (не искать и не качать): промпты, рубрики, бенчмарки,
  7 плагинов / 52 скилла (деплоятся `init` в `~/.arch-harness/plugins/`),
  дефолтные секции моделей deepseek/deepseek-pro/glm*/kimi/gigachat*.

## Шаг 1. Установка

```bash
mkdir -p ~/.local/bin && cp arch-be ~/.local/bin/ && chmod +x ~/.local/bin/arch-be
```

Файл из релиза GitHub называется `arch-be-linux-x86_64` (без exec-бита):
`cp arch-be-linux-x86_64 ~/.local/bin/arch-be && chmod +x ~/.local/bin/arch-be`.
Если пользователь скачивал релиз — сверь `sha256sum` с заметками релиза.

Проверка: `arch-be -V` → `arch-be 0.1.0`. Если `command not found` —
добавь `~/.local/bin` в PATH пользователя.

## Шаг 2. Инициализация

```bash
arch-be init
```

Проверка: существуют `CONFIG`, `~/.arch-harness/plugins/`,
`~/.arch-harness/mcp.json`. `init` идемпотентен по ассетам, но спроси
пользователя перед повторным запуском поверх настроенного конфига.

## Шаг 3. Ключи — СНАЧАЛА СПРОСИ ПОЛЬЗОВАТЕЛЯ

Секреты — только с ведома пользователя. Спроси, какие провайдеры нужны
и где лежат ключи (env уже выставлен? файл? выдать сейчас?). Затем:

- env уже выставлен → ничего не делать, иди на шаг 4;
- ключ передан → `export <ИМЯ>=...` в `~/.bashrc` пользователя
  (`DEEPSEEK_API_KEY` / `ZHIPU_API_KEY` / `KIMI_API_KEY`), значение
  не печатать и не повторять в выводе;
- ключ в файле → прописать `api_key_file = "~/.<name>_key"` в секции модели.

Проверка: `[ -n "$DEEPSEEK_API_KEY" ] && echo ok` (по каждому нужному
провайдеру; значение не выводить).

Если DeepSeek среди провайдеров нет — поставь в `CONFIG`
`default_model = "glm"` (или `"kimi"`): дефолт — deepseek, и запуск
без `--model` упрётся в отсутствующий ключ.

## Шаг 4. Диагностика

```bash
arch-be doctor
```

Приёмка: строка `Итог: 0 проблем`. Предупреждения о ключах неиспользуемых
моделей и о placeholder-каталогах knowledge — допустимы.

## Шаг 5. Приёмочный прогон (облачные LLM)

Для каждого затребованного провайдера:

```bash
arch-be run -q --timeout 90  --model deepseek "Ответь ровно одним словом: столица Франции?"
arch-be run -q --timeout 120 --model glm      "Ответь ровно одним словом: столица Японии?"
arch-be run -q --timeout 90  --model kimi     "Ответь ровно одним словом: столица Китая?"
```

Приёмка: exit 0, stdout — одно осмысленное слово. Известные факты
(сверено прямыми вызовами без прокси 2026-09-07): api.deepseek.com,
api.z.ai и api.kimi.com из РФ доступны напрямую; api.moonshot.ai
душится DPI — у kimi должен оставаться
`base_url = "https://api.kimi.com/coding/v1"`. Если endpoint недоступен
из сети пользователя (DPI) — поле `proxy` в секции модели.

## Шаг 6. Локальная модель (если затребована)

1. Получи у пользователя URL сервера и проверь:
   `curl -s <base_url>/models | head -c 400` (OpenAI-совместимый
   endpoint: llama.cpp, vLLM, Ollama `/v1`, LM Studio, шлюз).
2. Допиши в `CONFIG`:

```toml
[models.local]
base_url = "http://<host>:<port>/v1"
model = "<точный id из /v1/models>"
api_key_env = "LOCAL_LLM_API_KEY"
max_tokens = 4096
timeout_secs = 600
context_limit = <реальный ctx сервера>
```

3. `export LOCAL_LLM_API_KEY=local` в `~/.bashrc` (сервер без auth;
   значение произвольное, но переменная обязана быть непустой).
4. Приёмка: `arch-be run -q --timeout 240 --model local "…"` → exit 0.
5. Ошибка `HTTP 400 … does not support tools` = модель без tool calls;
   харнесс агентный и шлёт tools всегда → сообщи пользователю, что нужна
   модель с поддержкой инструментов (проверено: Qwen3.x на llama.cpp/vLLM).

Веса с HuggingFace (если пользователь просит «модель с HF»): HF — склад
весов, не сервер. Форматы: safetensors → vLLM (`vllm serve <репо>` —
скачает сам), GGUF (репо с суффиксом `-GGUF`) → llama.cpp/Ollama
(`huggingface-cli download <репо> <файл.gguf> --local-dir ~/models`,
затем `llama-server -m <файл> --port 8080 -c 32768 --jinja` — `--jinja`
обязателен для tools, контекст от 32768: промпт харнесса ~14K токенов,
иначе `exceed_context_size_error`). huggingface.co из РФ нестабилен (DPI): зеркало
`HF_ENDPOINT=https://hf-mirror.com`, http-прокси через `HTTPS_PROXY`
(socks не поддерживается — при «Unknown scheme … socks://» убрать
ALL_PROXY), ModelScope, `ollama pull`. Приёмка та же: `curl
<base_url>/models` → точный id → прогон `run -q --model local`.

## Шаг 7. Контекстные папки (если затребованы)

- База знаний: реальные каталоги пользователя (НЕ симлинки) в
  `[knowledge].dirs`; placeholder-строки из init удалить. Приёмка:
  `arch-be kb "<доменный запрос>"` → ненулевые хиты.
- Плагины: каталог библиотеки пользователя в `[plugins].dirs` (плагин =
  `plugin.json` + `skills/<name>/SKILL.md`). Приёмка: `arch-be plugins
  list` показывает плагины пользователя.
- Глобальная память: `~/.arch-harness/MEMORY.md` (в системный промпт
  каждой сессии).

## Стоп-условия (эскалация к пользователю)

- Провайдер отвечает 401/403 после корректной установки ключа → ключ
  невалиден/отозван — сообщить, не подбирать.
- Региональная блокировка endpoint'а → сообщить, предложить поле `proxy`
  в секции модели; VPN/egress-шлюз поднимать только с разрешения.
- Нужна правка firewall, системных сервисов, ротация ключей → только
  по прямому указанию пользователя.
- Любое значение ключа оказалось напечатано → сообщить пользователю
  о необходимости ротации.
